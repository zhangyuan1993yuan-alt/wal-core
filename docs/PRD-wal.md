## 1. 产品定位与一句话价值主张

**一句话价值主张**：给撮合引擎装上一个"黑匣子 + 时光机"——交易进行中每一步操作都被高速、可靠地记录下来，系统崩溃后能照着记录把订单簿原样恢复，模拟回测时能保证每一次重放结果完全一致。

**产品定位**：一个**通用的、嵌入式的、高并发 WAL 日志框架**。它不是撮合引擎，也不做撮合逻辑；它是撮合引擎脚下那块"必须先写日志、再改内存"的地基。任何需要"崩溃恢复、可重放、可审计、可复制"的 Java 系统（撮合只是第一个客户）都可以直接嵌入使用。

## 2. 核心概念扫盲（写给不懂行的读者）

### 2.1 什么是 WAL？

**WAL = Write-Ahead Log，预写日志**。核心规则只有一条：

> **任何对内存状态的修改，必须先把"我要做什么"这条记录写到日志文件里，再真正去改内存。**

打个比方：WAL 就像轮船的航海日志——船长每下一个命令（"左满舵""减速到 10 节"）都先记在日志本上，再执行。哪怕船半夜断了电，第二天翻日志本就能知道断电前所有命令执行到哪一条，从断点继续。

对应到撮合引擎：

- 内存里有一本"订单簿"（挂着所有未成交的买单和卖单）
- 每来一个新委托、每撮合出一笔成交，**先写一条日志，再改订单簿**
- 哪怕进程突然崩溃，重启后把日志从头到尾**重放（replay）**一遍，订单簿就恢复到崩溃前最后一刻

### 2.2 撮合引擎为什么需要 WAL？（五大理由）

| # | 诉求 | 没有 WAL 会怎样 | WAL 怎么解决 |
|---|---|---|---|
| 1 | **崩溃恢复** | 进程一崩，内存里的订单簿全没了，未成交订单凭空消失，交易所需赔偿客户 | 重放日志，把崩溃前的订单簿原样重建 |
| 2 | **订单不丢（持久性）** | 客户的委托可能"已接收但没落盘"，崩溃后无法证明收到过 | 委托在进入撮合前先落 WAL，收到即可证明 |
| 3 | **审计合规** | 监管要求所有委托/成交可追溯，纯内存无法自证清白 | 日志追加写入、只增不改、附校验码，天然是审计底账 |
| 4 | **重建订单簿** | 每次重启要靠数据库慢慢回灌，分钟级 | 顺序读日志重放，秒级重建 |
| 5 | **主备复制** | 备节点无法知道主节点处理了哪些订单，无法热备 | 主节点写 WAL，备节点订阅并重放同一份日志，与主保持一致 |

### 2.3 为什么"顺序写"比"随机写"快？

- 机械硬盘：磁头不用来回跳，顺序写能跑满磁盘带宽；随机写磁头来回跳，速度差百倍以上。
- 即使是 SSD（没有磁头），顺序写也能让操作系统合并写请求、减少元数据开销，**稳定比随机写快一个数量级，且延迟抖动小**。
- WAL 的写入模式天然是**只在文件末尾追加（append-only）**，永远不修改已写入的部分——这正好踩中了存储设备最擅长的工作模式。**这就是 WAL 高性能的根本原因。**

### 2.4 什么是组提交（Group Commit）？为什么它是性能关键？

日志写到内存缓冲区很快（纳秒级），真正的瓶颈是**把缓冲区刷到磁盘（fsync）**——一次 fsync 通常要几百微秒到几毫秒。

- **每条记录都 fsync 一次**：100 万条订单/秒 = 100 万次 fsync，磁盘完全扛不住。
- **组提交**：把一眨眼间（比如 200µs 内）到达的几百上千条记录**攒成一批，只做一次 fsync**。每条记录的持久性成本从"一次 fsync"摊薄为"几百分之一一次 fsync"。
- 代价：个别记录的落盘确认多等了一小段（微秒级），换来吞吐量提升百倍以上。对于撮合场景，这是标准的、经过验证的取舍。

> 换个比喻：快递员送信。一封一封跑一趟（逐条 fsync）vs 攒一车一起送（组提交）。信件晚到 200 微秒，但快递车数量少 100 倍。

### 2.5 名词速查表

| 术语 | 通俗解释 |
|---|---|
| 追加写（append-only） | 只在文件末尾往后写，不修改、不删除已有内容 |
| 分段（segment） | 日志切成一个个固定大小的文件（如每段 256MB），写满换新文件，便于管理、归档、删除旧数据 |
| CRC 校验 | 给每条记录算一个"指纹"，读的时候重新算一遍对比，指纹不对说明这条记录坏了 |
| fsync | 强制让操作系统把数据真正写到物理磁盘（否则可能只是躺在内存里） |
| 重放（replay） | 从头到尾顺序读日志，把每条记录代表的动作重新执行一遍 |
| 游标（cursor） | "我现在读到第几条了"的书签，支持断点续读 |
| 稀疏索引 | 每隔 N 条记录记一次"第 X 条在文件的哪个位置"，像书的目录，定位记录不用从头翻 |
| 崩溃恢复（recovery） | 进程崩溃重启后自动扫描日志、修复损坏的尾巴、重放重建状态 |
| 截断（truncate） | 把写坏的、不完整的尾部记录直接砍掉，保证日志可以继续使用 |
| Checkpoint / 快照 | 把当前完整状态（如订单簿）存一份，之后日志只需从快照点开始重放，恢复更快 |
| SPI（Service Provider Interface） | Java 标准插件机制：框架预留"插槽"，第三方不用改框架代码就能插入自己的实现（如自定义压缩算法、存储介质） |
| 幂等 / 去重 | 同一条消息重复到达时，保证只生效一次 |
| RTO（恢复时间目标） | 从崩溃到恢复服务所需时间的承诺上限 |

## 4. 需求池（P0 / P1 / P2）

> 优先级定义：**P0 = Must have**（没有就不算可用产品）；**P1 = Should have**（第一版应尽量包含）；**P2 = Nice to have**（规划但非首版必需）。每条需求附**可量化验收标准**。

### 4.1 P0 —— 必须有（核心可用性）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| WAL-P0-01 | **追加写入 API**：提供 `append(partition, data)` 返回唯一递增序号（seq），纯追加、只增不改 | ① 并发调用返回的 seq 全局唯一且单调递增，无空洞；② 写入 1 亿条记录后文件大小 = 记录总字节数（无额外放大 > 5%）；③ 单线程无 fsync 场景下，单条 append 纯内存耗时 p99 ≤ 2µs |
| WAL-P0-02 | **分段文件轮转**：日志按配置大小（默认 256MB）切分为多个 segment 文件，自动创建新段 | ① 写满阈值后自动滚动到新文件，旧文件保持只读不再被写；② 文件名含起始 seq/编号，字典序即时间序；③ 轮转过程对写入方零阻塞（不产生 > 1ms 的延迟尖刺） |
| WAL-P0-03 | **记录校验（CRC）**：每条记录写入时附 CRC32（或 CRC64）校验码，读取时校验 | ① 人工损坏任一 record 的任一字节后，读取方能检出并报错（错误检出率 ≥ 99.999%）；② 校验带来的单条开销 p99 ≤ 1µs |
| WAL-P0-04 | **组提交 + 可配置 fsync 策略**：支持至少 3 种策略——`ALWAYS`（每批必刷）/ `BATCH`（攒批定时刷，默认）/ `PERIODIC`（仅按时间间隔刷）；批大小与刷盘间隔可配置 | ① `BATCH` 模式下，配置 200µs 刷盘间隔 + 8KB 批阈值时，单机吞吐 ≥ 100 万条/秒（记录 256B，普通 NVMe SSD）；② 刷盘由独立后台线程执行，写入线程永不直接调用 fsync（`ALWAYS` 除外，由其自带语义决定）；③ 策略可在创建实例时指定 |
| WAL-P0-05 | **崩溃恢复（含尾部截断修复）**：启动时自动扫描最后一个 segment，校验每条记录；发现尾部写坏的记录（半条、CRC 错）时自动截断到最近一条完整记录，并重放回调给使用方 | ① kill -9 后重启：能恢复至崩溃前最后一条**完整落盘**的记录，无数据损坏扩散；② 人为在文件尾部追加 1~4096 字节垃圾后重启：被正确截除，日志可继续追加，恢复成功率 100%（单元测试覆盖 ≥ 20 种损坏形态）；③ 重放期间提供进度回调；④ 恢复完成后日志 seq 连续无空洞 |
| WAL-P0-06 | **顺序读取 / 游标**：提供按 seq 顺序读取 API 与持久化游标，支持从任意 seq 开始读 | ① 从任意 seq 开始顺序读取，返回记录与写入内容逐字节一致；② 游标重启后能从上次位置继续，不丢、不重；③ 顺序读取吞吐 ≥ 300MB/s（NVMe SSD，单线程） |
| WAL-P0-07 | **稀疏索引**：每 N 条（默认 1000）记录一个索引条目（seq → 文件内偏移），支持 O(log n) 定位任意 seq | ① 给定任意 seq，定位耗时 p99 ≤ 10µs；② 索引内存占用 ≤ 每条目 32 字节 × 记录数/1000 |
| WAL-P0-08 | **并发多分区写入**：支持多个分区（partition，如按 symbol/品种分）并行写入，分区间无锁或锁竞争极低 | ① 16 分区 × 每分区 1 写入线程，各分区吞吐相对单分区衰减 ≤ 10%；② 分区数支持配置到 ≥ 64 |
| WAL-P0-09 | **SPI 插件扩展点**：至少预留 5 类扩展接口——① Record 编码器（codec）② 存储介质（storage，文件系统之外可替换）③ 索引实现 ④ 保留策略（retention）⑤ 复制/订阅（replication）。通过 Java `ServiceLoader` 加载 | ① 提供每类接口的完整 Javadoc + 至少 1 个内置默认实现 + 1 个示例第三方实现；② 替换任一插件不需要重新编译框架代码，只需在 classpath 放新实现；③ SPI 加载失败时有明确错误信息指明缺失的实现 |
| WAL-P0-10 | **优雅关闭 flush**：`close()` 时保证所有已 append 但未刷盘的记录全部 fsync 落盘后再退出 | ① close 后立即 kill -9，重新打开无任何数据丢失（100% 记录可读且 CRC 正确）；② close 期间新 append 被拒绝并返回明确错误码 |

### 4.2 P1 —— 应该有（首版尽量包含）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| WAL-P1-01 | **实时 tail 订阅**：低延迟追随者（如备节点、实时风控）可订阅"新写入的记录"，延迟极小 | ① 订阅者收到记录的时刻 − 记录写入时刻 p99 ≤ 200µs（同进程内）；② 订阅者可指定从任意历史 seq 开始先追历史再追实时；③ 订阅者处理慢时不阻塞写入方（有界缓冲，溢出有明确策略：报错或断开可配） |
| WAL-P1-02 | **快照 + 日志截断（checkpoint & truncate）**：使用方可保存状态快照，之后删除快照点之前的旧日志 | ① 打快照后删除 N 个旧 segment，读取 seq ≥ 快照点不受影响；② 恢复时自动加载最近快照 + 重放其后日志，恢复耗时相比全量重放降低 ≥ 80%（日志量足够大时） |
| WAL-P1-03 | **保留策略**：按时间（如保留 7 天）或按总大小（如保留 500GB）自动清理旧 segment，策略可通过 SPI 替换 | ① 同时满足两种维度时以更严格的为准；② 清理不阻塞正常读写；③ 被 tail 订阅者尚未消费的文件不会被清理（可配置是否强制） |
| WAL-P1-04 | **动态增删分区**：运行期可创建/停用分区，无需重启 | ① 新建分区立即可写，首个记录 seq 从该分区独立序列正确开始；② 停用分区后写入收到明确错误，已写入数据仍可读 |
| WAL-P1-05 | **指标埋点**：内置 Micrometer 兼容的指标——写入吞吐（条/s、字节/s）、延迟分位（p50/p99/p999）、组提交批大小分布、日志总大小、刷盘耗时 | ① 每项指标有名称、单位、说明文档；② 可通过一行代码接入用户已有的 Micrometer Registry；③ 指标收集本身开销 < 总写入耗时 1% |
| WAL-P1-06 | **幂等去重**：可选地为每条记录指定业务幂等键，恢复/重放时同 key 记录只生效一次 | ① 重复写入同 key 1 万次，读到的生效记录恰为 1 条；② 幂等检查开销 p99 ≤ 1µs（纯内存路径）；③ 功能可关闭（默认关闭，避免影响性能） |

## 5. 非功能需求与量化指标表

| 类别 | 指标 | 目标值 | 备注 |
|---|---|---|---|
| 写入延迟 | append p50 | ≤ 5µs | 纯内存路径（不含 fsync 等待） |
| 写入延迟 | append p99 | ≤ 100µs | 含组提交等待时间，BATCH 策略 |
| 写入延迟 | append p999 | ≤ 1ms | 触发轮转/重试等边界场景 |
| 吞吐 | 单分区写入 TPS | ≥ 60 万条/秒 | 256B/条，BATCH 策略，NVMe SSD |
| 吞吐 | 整机（16 分区）总 TPS | ≥ 100 万条/秒 | 同上；受磁盘带宽上限约束 |
| 恢复能力 | RTO（恢复时间目标） | ≤ 30s | 前提：最近快照 + 单段（256MB）日志重放；全量重放 10GB ≤ 5 分钟 |
| 可靠性 | 已确认写入丢失率 | 0 | fsync 确认返回后的记录不允许因崩溃丢失 |
| 容量 | 单机支持日志总规模 | ≥ 10TB | 依赖保留策略+归档不撑爆磁盘 |
| 容量 | 日增日志量（撮合场景估算） | ≤ 500GB/天 | 按 100 万 TPS 峰值×30% 平均利用率×256B ≈ 日均 660 亿条折算上限；典型场景远低于此 |
| 资源 | 常驻堆外内存上限 | ≤ 512MB（默认配置，可调） | 堆内对象趋近于 0，避免 GC 抖动 |
| 资源 | 单核 CPU 占用 | 写入路径 100 万 TPS 时 ≤ 1 核（不含 fsync 系调用开销） | |
| 兼容性 | 运行环境 | Java 17+，Linux x86_64 主力支持，Windows/macOS 可运行（性能不承诺） | mmap 在 Windows 上文件锁行为有差异 |
| 质量 | 单元测试覆盖 | 核心模块行覆盖率 ≥ 80%，崩溃恢复场景 ≥ 30 个用例 | 含 kill -9 注入测试 |

## 6. 明确不做的事（Out of Scope）

| # | 不做的事 | 理由 |
|---|---|---|
| 1 | **不做 SQL/查询引擎**：不提供按内容查询、过滤、聚合能力，只按 seq 顺序读 | WAL 是"顺序事实流水"，查询是上层系统的职责 |
| 2 | **不做跨机房强一致共识的完整实现**（Raft/Paxos 只留 SPI 接口 + 参考适配层，P2） | 共识实现复杂度不亚于本项目本身，且强依赖具体部署拓扑 |
| 3 | **不做撮合业务逻辑**：不解析订单字段、不做价格/时间优先级撮合 | 本框架是地基不是房子；撮合引擎是使用方 |
| 4 | **不做独立网络服务**：不提供跨进程 RPC 接口，仅嵌入式 JAR | 用户已确认形态；进程内通信才能保证 µs 级延迟 |
| 5 | **不做多语言 SDK**：不提供 C++/Python/Rust 客户端 | 首版聚焦 Java 撮合生态；预留编码 SPI 便于未来兼容 |
| 6 | **不做日志加密**：透明加密交由文件系统层（如 LUKS）或未来编码插件 | 避免首版复杂度膨胀 |

## 7. 关键设计权衡

| # | 权衡点 | 选项 | 优点 | 缺点 | 我们的选择 |
|---|---|---|---|---|---|
| 1 | 文件读写方式 | **A. mmap（内存映射文件）** | 写入零拷贝、延迟极低；OS 自动管理刷页 | 页缓存抖动、TB 级映射管理复杂、fsync 语义间接 | **A（mmap 为主）**，但刷盘纪律由 fsync 策略严格约束（P0-04） |
| | | B. O_DIRECT + 自管理缓冲 | 绕过页缓存，延迟可预测性强，无双重缓存 | 编程复杂（需对齐）、小写入性能差、Java 支持需 JNI |  |
| | | C. 普通 FileChannel.write | 实现最简单、最可移植 | 每次写有系统调用开销，µs 级延迟目标难达成 |  |
| 2 | 日志组织 | A. 单一大日志文件 | 实现简单，全局 seq 天然单调 | 锁竞争集中在一点，多分区并发无从谈起；文件无法独立删除 | **B（多分区 × 分段）** |
| | | **B. 多分区日志（每分区再分段）** | 分区间无锁并发，扩展性最好；段可独立归档/删除 | 全局 seq 需映射为（分区, 分区内 seq） |  |
| 3 | 持久化策略 | A. 同步逐条 fsync | 任何时刻崩溃最多丢 1 条；延迟最高的方案（每次几百 µs~ms） | 吞吐撑不过 1~2 万 TPS，撮合完全不可用 | **B（组提交）** |
| | | **B. 组提交（攒批定时刷）** | 吞吐提升 100 倍量级，延迟可控可配 | 单条记录极端情况多等一个批周期（默认百 µs 级） |  |
| | | C. 纯异步（不管 fsync） | 吞吐最高 | 崩溃可丢数秒数据，"订单不丢"承诺破产 |  |
| 4 | 记录格式 | A. 存序列化对象（Java 序列化/JSON） | 直接可读、调试方便 | 体积大、反序列化慢、跨版本脆弱 | **B（原始二进制 + 轻量帧头）**；编码逻辑放 SPI，用户想序列化对象可自带 codec |
| | | **B. 存原始二进制字节 + 固定帧头（长度 + CRC + seq）** | 快、小、格式稳定，编码与存储解耦 | 肉眼不可读（提供 CLI 导出弥补，P2-04） |  |
| 5 | 索引粒度 | A. 每条记录都建索引 | 定位最快 | 索引体积与日志同数量级，得不偿失 | **B（稀疏索引，默认每 1000 条）**，粒度可配 |
| | | **B. 稀疏索引** | 内存占用小 3 个数量级；定位最多多顺序扫 999 条（µs 级） | 定位非 O(1) |  |
| 6 | 缓冲区位置 | A. JVM 堆内（byte[]） | 编码方便、调试简单 | 大缓冲引发 GC 停顿，违背"避免 GC 抖动"约束 | **B（堆外 DirectByteBuffer + 无锁队列）**，堆内只保留句柄与元数据 |
| | | **B. 堆外内存（off-heap）** | 无 GC 压力、与 mmap/IO 零拷贝衔接 | 需自行管理生命周期（泄漏防护要写测试） |  |

## 8. 待确认问题（影响架构决策，需用户拍板）

| # | 问题 | 为什么重要 | 默认建议（若用户不表态） |
|---|---|---|---|
| Q1 | **fsync 确认语义**：`append()` 返回成功，是否代表"已 fsync 落盘"？（这决定 API 是同步等待还是纯内存返回） | 直接决定延迟口径与"订单不丢"承诺的强度；撮合系统通常在"收到委托后回 ACK 前"需要一个同步刷盘点 | 提供双 API：`append()`（内存返回）+ `flushAndWait()`（同步刷盘），撮合在 ACK 前调用后者 |
| Q2 | **单条记录的典型大小**：订单/成交记录是 ~128B 小记录，还是可能带大 payload（如批量行情快照，数 KB~数十 KB）？ | 影响帧格式、批缓冲大小、CRC 开销占比与吞吐模型的准确性 | 按 128B~4KB 设计并压测覆盖两端 |
| Q3 | **分区数量级与 key 规则**：预计分区数是几十（按品种）还是上万（按账户）？ | 决定分区元数据结构（数组 vs 哈希表）与 mmap 段管理方式 | 按几百~几千设计，万元级降级可接受 |
| Q4 | **Windows 是不是一等公民**：生产部署在 Linux，但开发自测多在 Windows；mmap 的锁行为、fsync 语义在 Windows 有差异，是否需要 Windows 性能承诺？ | 决定是否要为 Windows 写降级实现（FileChannel 回退），增加测试矩阵 | Windows 可运行、正确性有保证，但性能指标只在 Linux 承诺 |
| Q5 | **恢复时是否需要框架"托管重放"**：崩溃恢复后，是只把记录按序回调给使用方（由撮合引擎自己重放重建订单簿），还是框架要内置"状态机快照恢复"流程？ | 前者框架更通用简单，后者撮合恢复更省事但框架沾业务味 | 前者（只回调），快照/重放编排通过 P1-02 的 SPI 让使用方自定义 |
