## 关键设计决定（后续维护必须知道）
- **性能口径分两个**：`append()` p99 ≤100µs（内存追加）；`flushAndWait()` 默认 p99 ~1.4ms。**"100 万 TPS"与"100µs 持久确认"单机 NVMe 物理上不可同时达成**（单次 fdatasync ≥80µs）
- 组提交走"无队列"方案：mmap 段本身就是环形队列，只传 dirtyMask 位图给刷盘线程
- 帧头 64B（=1 cache line），CRC32C 覆盖 `[0,20)∪[24,frameLen)`
- ARCH 文档 `TYPICAL_FRAME_LEN=328` 系算术错误，实际 320（已在 FrameLayout Javadoc 登记）
- `totalLogBytes()` 口径 = 数据字节（非段配置容量）；本版无在线 `verify()` API（等价能力=停机重开走恢复）
- `FAIL_FAST` 语义已收窄：仅"显式配置 id 未生效"或"有候选全不可用"时失败

## 开发过程中修掉的重点缺陷（10 个真实源码缺陷）
1. 恢复后读回 0 条（restoreAppendPosition 契约）
2. 逻辑截断不幂等（崩两次起不来）→ 物理截断
3. SKIP_RECORD 中间段静默丢数据 → resyncCount 也算损坏
4. 预建空段破坏 seek 二分（跳号）→ 恢复期清空段 + 有界回退
5. 每次轮转泄漏一个空段（rotateLocked 与 preparer 竞态）
6. FAIL_FAST 干净部署下永不可用
7. 长活游标 pin 整个分区 → 保留策略失效（QA 抓到）
8. 保留策略×游标竞态四连根因：段序列双写者无锁并发、删除 TOCTOU、readerCount 粒度、seekTo 早退无保护 → 段序列快照化 + LSN 围栏 + 三段式删除（QA 抓到）

## 流程经验
- 分批派单（T01-07 / T08-12 / T13-20+修复）+ 每批 IS_PASS + 诚实上报降级项，效果好
- QA 独立对抗性测试价值巨大：8 个用例抓出工程师 405 用例覆盖不到的静默缺陷（磁盘永不收缩、静默丢区间）；最终结论"建议交付（无保留）"
- **同目录并发跑 `mvn clean test` 会互相污染**（clean 删对方正在加载的 classes、surefire 报告互覆写），会产生"幽灵失败"，多人协作必须错峰独占
- "保留策略 + 长活游标"区域由 RetentionFenceRaceTest + QaRetentionPinnedCursorTest 双层守护，改此区域必须全量回归
